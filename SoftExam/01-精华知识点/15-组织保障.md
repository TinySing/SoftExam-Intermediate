# 第 15 章 组织保障

> [!important] 本章定位
> 组织保障的核心是让信息、文档、配置和变更可追溯、可控制、可复现。案例常考“谁能改、改什么、在哪改、如何批准、怎样回退”。

## 1. 信息与文档管理

### 文档分类

- 管理类：章程、计划、报告、会议纪要、问题和风险记录。
- 技术类：需求、设计、接口、代码说明、测试和部署文档。
- 合同类：招标文件、合同、变更、验收、付款和索赔资料。
- 运行类：配置、操作、备份、监控、故障和维护记录。

### 管理要求

文档应有唯一名称或编号、版本、状态、作者、审核人、批准人、日期、适用范围和存储位置。重要文档要控制访问权限、保留历史版本并可检索。

```text
产生 → 编号 → 审核/批准 → 发布 → 使用 → 更新/废止 → 归档
```

> [!warning] 易错
> 群消息、口头承诺和个人电脑文件不能自动成为正式项目记录；关键决策必须形成可追溯记录。

## 2. 配置管理

配置管理是在整个生命周期内识别配置项、记录其状态、控制变更、维护一致性并进行审计。

### 主要活动

1. 制定配置管理计划。
2. 配置项识别和命名。
3. 建立配置库和配置基线。
4. 记录配置状态和版本。
5. 实施配置变更控制。
6. 开展配置审计和报告。

### 配置项

需求、范围说明书、设计、代码、测试用例和报告、构建脚本、部署参数、项目计划、合同、用户手册、运维手册和交付成果等，都可能成为配置项。

### 配置库与基线

- 开发库：开发人员受控使用和修改。
- 受控库/主库：评审通过后统一管理的版本。
- 产品库/静态库：正式发布、交付和归档版本。
- 基线：经正式评审批准，作为后续变更依据的配置项集合。

配置项状态通常经历草稿、评审、批准、发布、修改和废止。具体库名称可按组织制度执行，关键是权限和状态清晰。

### 配置审计

- 功能配置审计：检查配置项是否满足需求和功能要求。
- 物理配置审计：检查配置项是否完整、版本和标识是否正确、文档与产品是否一致。

## 3. 变更管理

变更管理控制项目基准、产品、配置项和文档的修改，避免未经授权的范围蔓延和版本失控。

### 变更流程

```text
提出变更 → 记录变更请求 → 分类和优先级
→ 影响分析 → 评审和授权 → 更新基准/计划/配置
→ 实施与测试 → 验证 → 通知并关闭
```

影响分析至少覆盖范围、进度、成本、质量、资源、风险、采购、合同、安全和收益。

### 角色职责

- 变更提出人：说明原因、内容和期望。
- 项目经理：组织分析、协调执行和跟踪。
- 技术/业务负责人：评估技术、业务和交付影响。
- 变更控制委员会（CCB）或授权人：按权限批准、拒绝或延期。
- 配置管理员：维护基线、版本、状态和审计记录。

### 发布与回退

发布前要有版本标识、发布说明、测试结论、审批记录、备份、窗口、责任人、监控指标和回退条件。回退方案应提前验证，不能等失败后临时编写。

## 4. 组织保障案例答题

遇到“开发人员直接改生产、测试版本和生产版本不一致、文档找不到”：

1. 识别配置项和基线。
2. 统一配置库和版本管理。
3. 限制生产权限，落实职责分离。
4. 通过变更请求和 CCB 审批。
5. 发布前测试、审计、备份和回退演练。
6. 更新配置状态、发布记录和经验教训。

## 本章背诵清单

- [ ] 配置管理六项活动：识别配置项、记录配置状态、配置核实与审计、配置控制、配置报告、版本管理。
- [ ] 配置项=受控对象；基线=经批准的基准版本；配置库=存放配置数据；配置审计=检查配置记录与实际是否一致。
- [ ] 变更流程：提出→记录→影响分析→评审审批→更新基准和配置记录→执行→验证关闭。
- [ ] 发布前必须完成测试、审批、备份和回退方案确认。
